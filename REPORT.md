### Как писались графы в этом раунде — и что это значит для цифр

Два эталона написаны мной руками. Двадцать две задачи писали четыре субагента (Claude)
параллельно, каждый по справочнику `docs/FORMAT.md` и двум эталонам, **без права менять
рантайм**: каталог был заморожен на весь прогон, как требует план. Проверки к задачам писали
те же агенты, что и графы, — дисциплина «тесты скрыты» не соблюдена и в этом раунде.
Каждый агент вёл `NOTES.md` с тремя разделами: ослабленные проверки, промахи, что было новым.
Это не замер эксперимента, а инструмент роста формата: цифры ниже — атрибуция промахов,
не стоимость жизненного цикла.

### Учёт промахов по трём счётчикам

Ни одного промаха не закрыто по ходу прогона — каталог был заморожен. Все промахи записаны
в `apps/*/NOTES.md`; сводка по классам (число задач, где промах встретился):

- **Новые виды узлов** (то, что дороже всего): экспорт или печать отчёта (5), фоновые
  задания и таймеры (2: авто-поиски, отложенные письма), многошаговая форма-визард (1),
  права на поле и по роли на форме (1), редактируемые в рантайме варианты enum (1),
  пагинация и пользовательская сортировка (2), чат-интерфейс и LLM (1), графики (1),
  статус по времени (1), картинки и галереи (1), карты (1), точность денег больше двух
  знаков (1), карта мест (1), поле «время суток» (2), календарь (2), генерация документов
  (1), кнопки внешнего вида и адаптивность (3), панель со списком строк (1).
- **Новые коннекторы**: платёжный шлюз (9 задач из 22 — самый частый промах раунда), SMS
  (1), блокчейн (1), внешние системы бронирования (1), входящий или опрашивающий коннектор
  данных (1). Обратите внимание: `http` наружу есть, но агентам он был запрещён по
  техническим причинам прогона, и почта шла транспортом стенда.
- **Новые блоки**: коррелированный агрегат или проверка пересечения дат (3: аренда, авто,
  кемпинг — «занято ли на эти даты» невыразимо, потому что агрегат не видит текущую
  строку), арифметика дат `addDays` и `max` по датам (2), поиск по ключевым словам (1),
  argmin-агрегат «какая строка минимальна» (1), запись поля произвольной строки (1),
  условный шаг (1), утверждение на строке `check.assert` (1), движок сопоставления заявок
  (1), генератор дизайна (1).
- **Композиции** (выразимо, но криво): копия поля через события ради связанной таблицы в
  два прыжка (2), `own` на самой сущности пользователя (2), метка строки — первое текстовое
  поле, и выводимый текст её перехватывает (2), `after` на созданную строку (2), шаблоны
  писем данными (1), группировка панели через ссылку (1).

Чтение этих счётчиков по методике плана: виды узлов идут потоком (около двадцати разных
за 22 задачи), и большая их часть — про **представление** (экспорт, графики, календарь,
галереи, адаптивность), то есть про фронт, который план сознательно вынес за обещание.
Внутри бэкенда счётчик формата почти пуст: таймеры, поле времени суток, точность денег.
Коннекторы — один класс, платежи, и он закрывается дескриптором, а не новым узлом.
Блоки — один класс, коррелированные агрегаты, и это следующая правка алгебры выражений.

### Дефекты рантайма, найденные раундом

Шесть, все починены в тот же день, каждый накрыт тестом и мутацией:

1. После `db.createRow` контекст шага подхватывал id созданной строки как id текущей — и
   `{row.name}` в подтверждении называл чужую строку (нашли три агента независимо; в `shop`
   проходило только потому, что id совпадали).
2. Страница формы не показывала flash, на неё приземлившийся.
3. Чекер ложно видел цикл в `avg(Review: rating)`, разрешая имена внутри агрегата против
   внешней сущности.
4. `@me.email` отдавал id пользователя, хвост пути игнорировался.
5. Связанная таблица на странице строки показывала чужие строки, минуя `own`.
6. Отказ блока внутри события `created`/`updated`/`deleted` отвечал 500 вместо 400.

Плюс один порядковый дефект инструмента: мутационный гейт правил файлы рантайма на диске
как раз тогда, когда агенты гоняли проверки; один агент успел заложить в план «db.each
игнорирует where». Гейт и живые прогоны нельзя запускать одновременно — это теперь правило.

### Что стоит приложение на этом рантайме (замер, не оценка)

`apps/shop`, Node 22, один процесс, SQLite в файле, тихая машина:

| метрика | значение |
|---|---|
| старт до первого ответа | 395 мс |
| память после старта | 76 МБ (голый Node без кода — 56 МБ) |
| память после 2400 запросов | 116 МБ |
| список товаров, p50 / p99 | 1.6 / 3.1 мс |
| страница товара, p50 / p99 | 1.2 / 3.1 мс |
| корзина с выводимыми полями, p50 | 1.9 мс |
| действие с записью и транзакцией, p50 / p99 | 4.3 / 7.7 мс |
| пропускная способность, 20 параллельных | 1650 запросов/с |
| процессорное время на запрос | 1.2 мс |
| файл базы после прогона | 32 КБ |

Пол — сам Node: 56 МБ и сотни миллисекунд старта нельзя убрать, не сменив язык рантайма.
Рантайм поверх него добавляет 20 МБ и делает запрос за миллисекунду; для стенда и первых
замеров это не ограничение. Переписывать на Go или Rust сейчас — значит поддерживать две
реализации формата, который ещё растёт; это имеет смысл после стабилизации формата, и
граница плагинов должна быть к этому готова (объявления в данных, а не в коде ядра).

### Чего этот раунд по-прежнему не доказывает

- Браузерный агент бенчмарка не запускался: проверки — HTTP-сценарии авторов графов.
- Бейзлайнов нет: не с чем сравнить ни токены, ни регрессии.
- Графы задач писали субагенты, видевшие свои же проверки; каталог был заморожен, поэтому
  «промах» здесь — запись в NOTES, а не измеренная стоимость дописывания блока.

- **Составных блоков — 0** (композиции в языке пока нет).
- **Новых примитивных блоков — 3** (`db.createRow`, `random.pick`, `check.matchRef`).

Два блока, добавленных «на будущее» (`db.createIn`, `db.setOnRelated`), удалены: их не
использовало ни одно приложение. Каталог выводится из приложений, а не угадывается.

### Дефекты рантайма, найденные приложениями

Все четыре — на одной границе: **объявленное умолчание против присланного значения**.

1. Приведение булева поля не понимало числовую единицу — `db.toggle` тихо писал ноль.
2. `ALTER TABLE ADD COLUMN` не досевал объявленное умолчание: старые строки оставались с NULL.
3. Снятая галочка на создании молча превращалась в объявленное умолчание `true` — неактивная
   вакансия попадала в список активных.
4. Переписывание рантайма ради общности сломало два зелёных теста `todo` (подписи булевых
   полей и меню). Поймано повторным прогоном — ровно то, для чего в плане золотые трассы.

Отдельно — три дефекта **самого стенда проверок** (регулярка для id, экранированный апостроф,
мусорный `fetch`). Их стоит считать отдельно: они не говорят о языке ничего, но показывают,
что проверки нужно проверять.

### Где мои проверки слабее оригинальных тестов

Это важнее приятных цифр:

- **studygroups, тест 2**: оригинал требует, чтобы ресурс **скачался файлом на устройство**.
  В графе есть только ссылка, файлов рантайм не умеет вовсе. Моя проверка принимает ссылку —
  то есть проверяет более слабое утверждение. Это **непокрытый промах**: нужен коннектор файлов.
- **internships, тест 2**: оригинал требует **письмо-подтверждение** заявки. Письма никто не
  шлёт; моя проверка принимает подтверждение на экране. Нужен коннектор почты.
- **campus, тест 6**: оригинал говорит о «получении уведомления», у нас уведомление появляется
  строкой в списке, а не доставляется.

То есть из 68 проверок **три проверяют ослабленное требование**, и все три упираются в один
и тот же пробел — наружу приложение не ходит.

### Чего этот прогон по-прежнему не доказывает

- Браузерный агент бенчмарка не запускался: тесты переведены в HTTP-сценарии мной.
- Приложения и проверки писал один автор — дисциплина «тесты скрыты» не соблюдена.
- Бейзлайнов нет: не с чем сравнить ни токены, ни регрессии.
- Задачи «за краем класса» выбраны мной, а не жребием.

Прогон показал, что **конструкция держит одиннадцать разных приложений при семи блоках** —
и по-прежнему ничего не сказал о том, что она выигрывает у обычного кода.
