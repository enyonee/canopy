# baseball — webgen-bench/000012

## Weakened cases

- **Case 2 (real-time play-by-play).** The instruction is never mentioned alongside accounts, so —
  like apps/game2048 — this app has no `/roles`; anyone can simulate. Creating a `Game` (the
  standard entity form) simulates it completely, synchronously, via a `Game.created` event: there
  is no background job or push channel in this format (see docs/FORMAT.md's stated non-promises),
  so "real-time" is read as "the play-by-play log is real and complete the moment the game exists",
  not literally streaming. Every play is a genuine `Play` row (inning, half, description, running
  score) generated by an actual inning-by-inning simulation with base-running, not canned text.
- **Batting average is stored/shown as thousandths (e.g. `275` meaning `.275`), not `money`.** A
  derived field's expression kind must match its declared kind, and `hits / atBats` (both `int`
  fields) type-checks as a plain number — there is no cast to force a `money`-kind result out of
  int arithmetic (see Misses). `round(hits * 1000 / atBats, 0)` keeps the number honest and precise
  without pretending it is a dollar amount.
- **Defense strategy only has one real effect on the sim**: it shifts the *fielding* team's out
  probability by a fixed amount (aggressive fields for a few more hits through, conservative fields
  a few more outs) — enough to change outcomes measurably and deterministically (checked against
  the engine's own prediction under both settings), not a full tactical model.

## Misses

- `field kind` — a derived field's declared kind must match its expression's inferred kind
  one-for-one (`runtime/check/data.mjs`); there is no way to derive a `money` value from `int`
  arithmetic (multiply/divide two `int` fields) without the checker calling it a mismatch. Cost a
  checker error before `battingAvg` was redeclared as `int` (thousandths) instead of `money`.
- `composition` — same recorded miss as apps/chess and apps/poker: a global action's
  `db.createRow` never fires the created entity's `created` event, so "create a game and
  immediately simulate it" only works because `Game` is created through the *standard* entity form
  (whose route does fire `Game.created`) — a bespoke "new game" global action would have needed a
  hand-rolled insert+simulate block instead, same as those two apps' own workarounds.
- `composition` — no way to give a bare `detail.actions` button its own input fields (only a
  `states` transition's `fields` can collect input on a button press) — this is *why* adjusting
  defense strategy and the budget split are ordinary edits of `Team.form` (with the real business
  rule "neither budget may go negative" living in `/rules`) rather than dedicated actions; simpler
  in the end, but only because the alternative was not directly available for a plain action.
- `node kind` — no scheduled/background step (Round-4's `schedule` node exists but was judged the
  wrong fit here — see the note below); a truly "live" simulation would need one.

## New for this app

- A third from-scratch pure engine (`apps/baseball/engine.mjs`, same "kept out of plugins/,
  imported by both the server and checks.mjs" shape as chess's and poker's): seeded inning-by-
  inning simulation with real (if simplified — no baserunning outs/errors) base-state advancement,
  producing a deterministic score and play-by-play from nothing but a seed and two lineups.
  Verified by hand that "aggressive" vs "conservative" defense measurably and consistently shifts
  total runs scored across many seeds before being wired into the app.
- A batter's cumulative season stats (`atBats`/`hits`/`homeRuns`/`rbis`) are updated from the
  simulation's own per-batter deltas, not just the final score — `checks.mjs`'s case 1 depends on
  this being real data, not a placeholder.
- Considered `schedule` for the "real-time" requirement (Round-4's prescribed tool for exactly this
  kind of ask) and deliberately did not reach for it: this task's simulation is a discrete, finite
  event (one game, computed once) rather than an ongoing accrual a tick should advance — `schedule`
  is used instead, as intended, in apps/strategy's resource ticks.
