# Тесты рантайма

Гейт из плана: пока рантайм не доказан, любая цифра эксперимента мерит мои баги, а не язык.

```bash
node --test 'tests/*.test.mjs'                                              # прогон (включает tests/arch.test.mjs и tests/perf.test.mjs)
node tests/coverage.mjs                                                     # покрытие: гейт, красный при < 100% строк
node tests/mutate.mjs                                                       # мутационный гейт
node tests/mutate.mjs "money"                                               # только мутации с этим словом в имени
npx tsc -p .                                                                # типы (JSDoc + runtime/types.d.ts)
node verify/run.mjs                                                         # приёмочные проверки всех приложений
npm run bench                                                               # boot/RSS/p50/p95 на бенч-графе — информационно, не гейт
npm run gate                                                                # test + coverage + types + mutate, в этом порядке
```

Зависимостей нет: `node:test`, `node:assert`, встроенное покрытие Node 22 —
`tests/coverage.mjs` запускает его само (`--experimental-test-coverage` плюс LCOV-репортёр)
и парсит проценты по файлам, `package.json`'s единственная dev-зависимость — `typescript`
(и `@types/node` для `node:`). Исходящий HTTP в тестах подменён (`fakeFetch` в
`tests/helpers.mjs`): записывает вызовы и отвечает тем, что скажет тест.

## Архитектурные гейты (`tests/arch.test.mjs`)

Часть обычного прогона (`node --test`), не отдельная команда. Парсит исходники рантайма
(строки/скобки/импорты — маскируя строки, шаблонные литералы и комментарии до пробелов,
метод задокументирован в самом файле) и падает, если:

- **модуль длиннее 300 строк** или **функция/метод длиннее 60** (скобочный разбор на
  замаскированном тексте — один god-function больше не разрастается незамеченным);
- **импорт не в явной таблице** слоёв (`runtime/ARCHITECTURE.md`'s таблица — та же, что в
  тесте) — новое ребро зависимости валит сборку; отдельная таблица — какому модулю какие
  `node:` встройки разрешены (`node:sqlite` только `driver/sqlite.mjs`, `node:http` только
  `server.mjs`, и т.д.); плюс поиск циклов;
- **SQLite-специфика вне `runtime/driver/`**: `DatabaseSync`, `PRAGMA`, `sqlite_master`,
  `AUTOINCREMENT`, `.prepare(`, `drv.exec(`/`db.exec(`, `this.db`/`store.db` — нигде, кроме
  драйвера (S1);
- **`catch {}`/`catch (e) {}` пустой** или с одним комментарием — без метки
  `// allow-swallow: <причина>`;
- **`catch`, превращающий ошибку в успех** (`ok = true`, `return true` вне `routes/`, где
  `return true` — контракт «запрос обработан», а не гашение ошибки) — без той же метки;
  ровно этот класс бага чинит `runtime/interp.mjs`'s `validateValues` в этом раунде
  (раньше — `ok = true` в `catch`, теперь — отказ с трассировкой ошибки);
- **`TODO`/`FIXME`/`XXX`, `console.log` вне списка стартовых строк** (`cli.mjs`, `patch.mjs`,
  `server.mjs`, `boot.mjs`), `debugger`, **закомментированный код** (2+ строки `//` подряд,
  которые парсятся как JS после снятия `//`);
- **мёртвый экспорт**: что-то экспортировано из `runtime/`, но не импортировано нигде в
  `runtime/`, `tests/`, `verify/`, `plugins/`, `apps/*/plugins/`;
- **вид узла без документации, чекера или теста**: `validate.mjs`'s `TOP` обязан совпадать
  с таблицей «Top-level nodes» в `docs/FORMAT.md`; у каждого — модуль в `runtime/check/`
  (`export const NODES = [...]`) и упоминание в каком-нибудь тесте;
- **реестр без контракта**: у каждого блока/типа поля/транспорта/функции/виджета — обязательные
  ключи (`summary,effects,requires,run` и т. д.; у виджета — `summary,client`), проверено и для
  встроенных, и для каждого плагина в `plugins/` и `apps/*/plugins/` (значит виджетский
  браузерный файл нельзя класть в `plugins/` — этот тест его вслепую импортирует как серверный
  модуль; см. `docs/FORMAT.md`'s «Клиентские виджеты» и `apps/tictactoe/plugins/ttt.mjs`).

## Мутационный гейт

Покрытие говорит «строка исполнилась». Гейт говорит «тесты заметили бы, будь она неверной».
`tests/mutate.mjs` вносит в рантайм по одной осмысленной поломке и требует, чтобы прогон покраснел.

Первые четыре мутации — это ровно те четыре дефекта, которые нашли первые одиннадцать
приложений: они обязаны ловиться навсегда. Вторая половина списка — то, что делает
формат v2 опасным, если сломать молча: неверный пароль пускает, поддельная сессия принимается,
`own` не проверяется, список показывает чужие строки, скачивание файла без прав, правило не
срабатывает, уникальность сталкивается с самой строкой, переход игнорирует статус или роль,
поля перехода необязательны, отказ блока коммитит сделанное до него, ящик не сбрасывается
после коммита, не-2xx считается доставкой, деньги хранятся в мажорных единицах или читаются в
минорных, `gte` значит `gt`, месяц группируется по дню, хеш попадает на страницу, чекер
пропускает недостижимый статус, неизвестную операцию, цикл, плохое выражение, неизвестный
узел или ссылку.

**Что гейт нашёл в этот раз.** При 100 % покрытия строк выжили четыре мутации из 75, и
каждая — дыра в утверждениях, а не в исполнении: (1) `by` у перехода не проверялось на
странице — кнопка предлагалась, а сервер отказывал; тест смотрел только на сервер;
(2) приоритет умножения над сложением исполнялся, но не утверждался; (3) `gte` против `gt`
не различался, потому что ни один тест не бил точно в границу; (4) пароль в колонке никогда
не проверялся — вместо теста на маскирование чекер теперь запрещает пароль в колонках, а
ветка рендера удалена. Плюс двенадцать старых мутаций перестали накладываться после
переписки рантайма — их образцы обновлены, все двенадцать по-прежнему убиваются.

Текущий результат: **97 из 97 мутаций убито** (последние семь перед этим раундом добавлены
под дефекты, которые нашёл второй раунд бенча: подмена строки после `db.createRow`, потеря
flash на форме, ложный цикл в агрегате, `@me.поле`, `own` в связанной таблице, отказ внутри
события). Это и есть содержательная часть покрытия — проценты сами по себе не значат ничего.

Раунд 3 — разбор `server.mjs`/`validate.mjs`/`store.mjs` на модули переточил все мутации,
которые целились в их код, на новые файлы (тот же текст, то же место в новой структуре —
см. `runtime/ARCHITECTURE.md`), не потеряв ни одной; плюс две новые под сам рефакторинг:
рефакторинг зафиксировал вход-в-систему-ли-гейт в `server.mjs`'s `dispatch()` (мутация
«anonymous access is never asked to sign in») и фикс fail-open в `validateValues` (мутация
«a throwing rule passes instead of refusing the write»).

Раунд 4 добавил четыре мутации под самый чувствительный новый код: секрет утекает в
JSON-ответ («a secret field reaches a JSON answer»), JSON-отказ тихо превращается в
HTML/редирект («a denied JSON request gets an HTML/redirect answer instead of a JSON body»),
ручной прогон расписания доступен не только оператору («anyone may run a schedule by hand»),
подпись оси графика показывает сырые минорные единицы вместо денег («a chart's axis label
shows raw storage units»). Итог раунда 4: **101 из 101 мутации убито**.

Раунд 5 добавил девятнадцать мутаций — по одной на каждый закрытый пробел (own с одним хопом,
общий предикат кнопки действия, `@row.*` в fill связанной формы, составная уникальность с
откатом на текущую строку, `db.set`, право на форму секции страницы, право на сущность в поиске,
событие `viewed`, `hours()`, `byRole`, копирование сидируемого файла, `id` в выражении, `created`
от блока и защита от цикла (две мутации), интерполяция `confirm`, `ne: null`, редакция `private`,
резолвинг `@row.*` в пропе виджета, обязательность полей действия) — плюс починка четырёх
мутаций, протухших после рефакторинга `auth.mjs`/`interp.mjs`/`routes/context.mjs` в этом же
раунде (те же дефекты, тот же текст, только на новом месте кода — метод из раунда 3 повторён).
Итог: **120 из 120 мутаций убито**.

Раунд 6 переехал (не размножил) четыре мутации на правила из `interp.mjs` в
`runtime/store/rules.mjs` — тот же дефект, тот же текст, новое место кода, ровно по конвенции
выше — и добавил две новые под сам гейт: отключить проверку правил внутри `Store#insert`/
`Store#update` («item 20: a block's own insert/update has no path to the rule guard») —
ни одна форма-ориентированная проверка её не ловит (форма никогда не доходит до
`store.insert`/`update`, когда `interp.validateValues` уже отказал раньше), поэтому убивают её
только `tests/interp.test.mjs`'s новые тесты — плагин-блок, пишущий прямо в `store.insert`, и
встроенный `db.update` внутри действия. Итог раунда 6: **122 из 122 мутаций убито**.

## Раунд 7: производительность

Индексы, выводимые из графа; paging до хайдрейта; батчинг агрегатов (N+1 → O(1) на всю
страницу, на любую глубину вложенности); prepared-statement cache; гейт по числу запросов.
Подробности — `runtime/ARCHITECTURE.md`'s «Кто чем владеет».

- **Индексы** (`runtime/store/migrate.mjs`, `tests/store.test.mjs`): каждое `ref`-поле
  (значит и каждое `own`-поле — оно обязано быть `ref:<roles.entity>`), каждое
  `rules.unique` (одиночное — обычный индекс, составное — составной), статусное поле
  `states`, и best-effort — верхнеуровневые ключи `where` в `lists`/`dashboards`.
  Создаются и удаляются как колонки: идемпотентно, детерминированные имена
  (`idx_<table>_<col…>`), удаление — безусловное (индекс не хранит данных).
- **Batched hydrate** (`runtime/store/query.mjs`'s `hydratePage`/`buildAggCache`,
  `runtime/store.mjs`'s `ctx()`/`derived()`/`hydrate()`): не паттерн-матчинг «плоский
  агрегат / коррелированный / вложенный» — прозрачный кэш на `ctx().rows()`. Для
  страницы строк одного вида собирается, рекурсивно на любую глубину, набор детей
  одним запросом на пару (потомок, поле-ссылка) вместо одного на строку; при
  промахе кэша (нет прямой ссылки назад — агрегат по всем строкам «сиблингов») —
  тот же запрос, что и раньше. Корректность поэтому не зависит от формы агрегата:
  `tests/perf.test.mjs`'s property-тест сравнивает батчевую и построчную гидратацию
  на случайных данных и требует побитового совпадения.
- **Page-before-hydrate** (`runtime/store/query.mjs`'s `listPage`, `runtime/routes/context.mjs`'s
  `paged`): без derived-сортировки и без in-memory `where` — `COUNT(*)` + `SELECT …
  LIMIT/OFFSET`, гидратируется только страница. Иначе — старый путь (полная гидратация,
  уже батчевая, срез в памяти) — результат тот же самый, просто без ускорения. Список
  сущности, сохранённый список, их JSON и секция страницы с `limit` — на новом пути;
  CSV по-прежнему гидратирует всё (документированное требование); дашборд с derived-полем
  в `metric`/`groupBy`/`where` (`aggregateInMemory`) получает батчинг бесплатно — он и
  раньше звал `store.list()`.
- **Prepared statement cache** (`Store#prepare`, bounded LRU на 200 записей по тексту SQL):
  каждый `this.db.prepare` в `store.mjs`/`store/*.mjs` заменён на `this.prepare`.
- **Перф-гейт** `tests/perf.test.mjs` (часть `npm test`) — не время, число запросов:
  список на 100 и на 2000 строках — одинаковое (маленькое) число запросов, включая
  вложенный агрегат (Customer.spent через Order.total через Item); CSV — то же самое;
  дашборд с derived-метрикой — то же самое; деталь с 2 и с 2000 дочерних — то же
  самое; `EXPLAIN QUERY PLAN` подтверждает индекс на прямой ссылке. Плюс
  property-тест (выше), плюс тест на саму `listPage`'а: полный-скан фолбэк (derived-сортировка
  или in-memory `where`) обязан по-прежнему резать на страницы, а не отдавать всё —
  единственная мутация раунда, которую не поймал первый набор тестов (`paging shows
  every row on every page (the full-scan fallback path)`), поймана этим тестом. Итого
  раунда 7: **+11 тестов** (240 → 251), **+9 мутаций** (122 → 131, из них 8 новых под

### Раунд 7, ревью оркестратора: три дефекта после первого прохода

Независимый бенч оркестратора (x1 и x4, JSON-снимки побайтово совпали до/после) нашёл
три вещи, которые первый проход раунда 7 не проверял:

- **(A) Квадратичный поиск лейбла.** Форма: один Customer, N Order
  (`Customer.spent := sum(Order: total)`). `GET /Order.csv`: N=2000 было 71 с
  (baseline — 515 с), N=4000 — 293 с. Причина: `render.mjs`'s `plain()` (и ещё пять
  мест — `fields.mjs`'s `ref.format`, `routes/views.mjs`:31,42, `render/dashboard.mjs`'s
  `groupLabel`+таблицы) читали лейбл через `store.label(target, store.get(target, id))`
  — `store.get` хайдрейтит **всю** строку цели, включая любой сколь угодно дорогой
  агрегат, только чтобы прочитать одно (обычно не производное) поле. Лейблу никогда не
  нужно ничего, кроме самого лейбл-поля. Добавлен `Store#labelOf(entity, id)`
  (`runtime/store/query.mjs`): читает сырую строку и вычисляет только лейбл-поле, и
  только если оно само производное. Подключён во всех шести местах. Гейт-тест в
  `tests/arch.test.mjs` статически запрещает паттерн `store.label(…, store.get(…))`
  где-либо в `runtime/` — не только сейчас закрытые места, но и будущие. Проверено
  репро-скриптом оркестратора (один Customer, N Order, `GET /Order.csv`): N=4000 —
  **99 мс** (было 293 с); `GET /Order` (HTML, страница) — 43 мс.
- **(B) Лимит числа переменных SQL.** `listRawIn` связывал каждый id в один
  `IN (…)`; предел SQLite (`SQLITE_MAX_VARIABLE_NUMBER`, 32766 с 3.32.0, было 999) —
  страница/CSV/дашборд с бо́льшим числом родителей не должны падать. `listRawIn`
  теперь режет список на куски по 5000 (`IN_CHUNK`) — запрос на каждый кусок вместо
  одного гигантского; сами куски **не кладутся в prepared-statement cache**
  (`this.db.prepare`, не `this.prepare`) — их SQL-текст меняется по числу параметров
  на границе, и кэширование их только вытесняло бы то, что реально переиспользуется.
  Тест на >32766 родителей (35000 строк, одна транзакция, ~0.4 с) — не падает.
- **(C) Порядок детей.** Построчный путь читал детей `ORDER BY id DESC` (умолчание
  `listRaw` без явного `sort`); батчевый `listRawIn` не заказывал порядок вовсе —
  плавающая сумма денег (мажорные единицы) могла округлиться иначе в последнем
  разряде. `listRawIn` теперь всегда `ORDER BY id DESC` — на каждый кусок, так что
  порядок внутри группы одного родителя тот же, что и раньше. Property-тест
  batched==per-row расширен: денежные значения вида 0.1/0.2/0.7 вперемешку со
  случайными, 4000 строк вместо 600 — плюс отдельный тест, сравнивающий порядок id
  внутри одной группы батчевого пути с порядком того же `listRaw` без батчинга.

Тесты: `tests/perf.test.mjs` — 5 новых (лейбл без хайдрейта; чанкинг `listRawIn`
структурно — число `prepare()`-вызовов; >32766 родителей не падает; порядок группы;
property-тест расширен на месте). `tests/arch.test.mjs` — 1 новый (статический гейт
на анти-паттерн лейбла). Мутации: 3 новых (A/B/C) плюс обновлены find-тексты двух
старых мутаций, которые задели те же строки («a reference renders as its raw id»,
«…IN-list is never coerced…»). Итого: **256 тестов**, **134 мутации**, все зелёные;
`node verify/run.mjs` — **699/699**.

## Раунд 8: агрегаты в SQL, регрессия памяти

Измерено на 0.1.1 (один Order с 20 000 Item, один Customer с 5000 Order):
`GET /Order/<wide>` 30.7 мс p50 (48.5 мс p95) — `total := sum(Item: qty *
price)` фетчил все 20 000 строк и считал выражение в JS на каждый запрос;
после тяжёлых `/dashboard` и `/Order.csv` на 2000/8000/40000 строк RSS росло
(батченные дети держались в памяти на весь запрос).

**Item 1: компиляция агрегата в SQL.** Новый модуль `runtime/store/aggsql.mjs`
(`compileAgg`) — компилирует `count`/`sum`/`avg`/`min`/`max` с прямым `via` в
одно `SELECT agg(...) ... WHERE via=?` (одиночная строка, `runAggOne`) или
`... WHERE via IN (...) GROUP BY via` (страница, `runAggBatch`, чанки как у
`listRawIn`), когда тело построено только из хранимых `int`/`money`/`bool`
полей ребёнка: арифметика `+ - *`, сравнения `= != < <= > >=`, `and/or/not`,
целые литералы, `if(cond,a,b)`. Всё остальное — производные поля внутри тела,
`row.*` (коррелированные), хоп через ссылку, дата/время, функции плагина
кроме `if`, деление где-либо в теле, дробный литерал, текст/enum/ref в
сравнении — фолбэк на прежний путь без изменений.

*Почему это побитово совпадает с JS.* Деньги и целые представлены как точные
целые в своём масштабе (деньги — минорные единицы, scale 100; число/литерал —
scale 1); `a op b` комбинирует масштабы домножением, а не делением на 100
посреди выражения — так что `SUM`/`MIN`/`MAX`/`COUNT` в SQLite видят только
целые (проверено против `BigInt`-эталона на 5000 случайных пар при написании)
и складывают их точно, независимо от порядка — свойство, которого не было бы
у суммы через `/100.0` внутри тела (SQLite's `SUM()` использует компенсированное
суммирование, отличное от наивного `reduce` в `expr.mjs`, так что порядок мог
бы разойтись в последнем разряде — ровно риск, которого архитектура избегает,
никогда не деля внутри тела). Единственное настоящее деление — одно, в конце,
на родителя, через тот же `exact()` (теперь экспортирован из `expr.mjs`,
не копия), которым пользуется `evaluate()`'s `sum`/`avg` — округление не
может разойтись между путями, потому что это буквально один и тот же код.
Пустая группа: `sum`/`count` — 0 (не SQL `NULL`; JS's `reduce(...,0)`), `avg`/
`min`/`max` — null, как и раньше. Сравнение с `NULL`-операндом компилируется
в `CASE WHEN a IS NULL OR b IS NULL THEN 0 ELSE (a op b) END` — SQLite отдаёт
`NULL` на `a < NULL`, `expr.mjs` всегда `false`; без этой обёртки `not(a<b)`
разошёлся бы (SQL: `NOT(NULL)` = `NULL` = «не выбрано», JS: `not(false)` =
`true`). Точка входа — `Store#ctx()`'s `agg(node)`, которую `runtime/expr.mjs`'s
`evaluate()` пробует первой в ветке `agg` (`ctx.agg`, опционален, `undefined`
= «веди себя как раньше»): работает и для одиночной строки (`Store#get()` —
ровно случай из брифа), и через `cache.scalars` (`buildAggCache`, batched)
для страницы. Рекурсия `buildAggCache` в дочернюю сущность (для некомпилируемых
агрегатов) сама эту же компиляцию находит на следующем уровне: `Customer.spent
:= sum(Order: total)` не компилируется («total» не хранимое поле), но при
рекурсии в `Order` его собственный `total := sum(Item: qty*price)` —
компилируется, так что даже некомпилируемый верхний агрегат не тянет за собой
некомпилируемость на всю глубину.

Property-тест (`tests/aggsql.test.mjs`) — случайные строки-дети (включая
отрицательные qty, `null` в discount, дробные деньги вида 0.1/0.2/0.7/0.01,
пустые родители) и весь набор компилируемых форм, путь SQL сравнивается с
путём JS (форсированным через временную подмену `Store#aggValue`) побитово
(`assert.deepEqual`) — и одиночная строка, и вся страница, и через границу
чанка (650 родителей). Плюс прямые unit-тесты границы компилятора
(`compileAgg` принимает/отклоняет ровно документированный список форм) —
точнее, чем полагаться на статистическое расхождение для веток вроде
«деление исключено» или «дробный литерал исключён». Расхождений JS-пути с
SQL-путём не найдено; переписывать семантику JS-пути не потребовалось.

**Item 2: регрессия памяти.** С item 1 большинство батченных фетчей детей
пропадает само — компилируемый агрегат никогда не читает дочернюю строку в
JS вообще (`tests/aggsql.test.mjs`'s тест оборачивает `listRaw`/`listRawIn` и
проверяет ноль вызовов). Для того, что осталось (некомпилируемый — например,
вложенный `Customer.spent` — или коррелированный агрегат) —
`runtime/store/hydrate.mjs`'s `hydratePage` режет страницу на чанки по 500
родителей: кэш агрегатов (`buildAggCache`) и любые сырые строки детей,
которые он всё же держит, живут на один чанк, а не на весь запрос — прежний
`hydratePage`/`buildAggCache` жили в `store/query.mjs`, переехали в новый
`store/hydrate.mjs` (тот же приём именования модуля, что у остального
`store/*`) заодно чтобы не пробить бюджет строк модуля. Измерено: RSS после
`/dashboard/sales` + `/Order.csv` на 40 000 orders/200 000 items — рост
+87 МБ (0.1.1) → +17 МБ (этот раунд), тем же скриптом, до и после
принудительного GC (`--expose-gc`, `npm run bench`).

## Раунд 9: производные поля, вложенные агрегаты и даты в SQL; память

Измерено на 0.1.2 (`bench/app2.json`, сценарий 4 в `npm run bench`: один клиент с
5000 заказов по 2 позиции + 200 клиентов по 10 заказов; поля клиента —
`spent := sum(Order: total)`, `lines := sum(Order: gross)` где `gross := sum(Item: line)`,
`big := count(Order: total > 100)`, `recent := count(Order: placed > '2026-01-01')`,
`latest := max(Order: placed)`, `late := count(Order: placed < today)`): ни одно из них
0.1.2 не компилировало — производное поле в теле, дата — и тянуло все заказы в JS.

**Item 1: производное скалярное поле ребёнка в теле.** `compileDerived`
(`runtime/store/aggexpr.mjs`) инлайнит выражение производного поля, скомпилированное
в scope ребёнка. Значение производного поля в JS — это `toExpr(fromExpr(evaluate(…)))`,
то есть *округлённое до хранимой формы*: money — до целых минорных единиц, int —
`Math.round`. Инлайнится только то, где это округление тождественно: money из
выражения со scale 1 (`× 100`) или 100 (как есть); int из scale 1. money*money
(scale 10000 — нужно настоящее округление половин от нуля) и int из money — нет.
bool — через `compileBool` (значение — 0/1, `v ? 1 : 0` из `fromExpr`).
Рекурсия ограничена тремя вещами: сам ключ `Entity.field` в стеке (цикл — не
компилируем, JS-путь бросает своё «depends on itself», как и раньше), длина стека
(8) и бюджет расширений на один план (200: граф, где каждое поле ссылается на
предыдущее пять раз, иначе сделал бы компиляцию экспоненциальной).

**Item 2: производный/вписанный агрегат внутри тела** — коррелированный скалярный
подзапрос: `COALESCE((SELECT SUM(…) FROM item AS t1 WHERE t1."order" = CAST(t0."id" AS TEXT)), 0)`.
Пустая группа: sum/count — 0 (COALESCE / COUNT сам), min/max — NULL и дальше как в
`expr.mjs` (значение `null` отфильтровывается из внешних sum/avg/min/max, в
сравнении даёт `false`). Внутренний `avg` — дробь, оставлен JS. Масштаб не делится
до самого внешнего агрегата (сырые минорные единицы внутреннего `sum` идут внешнему
`SUM` как есть). **Join по `CAST(id AS TEXT)` — не косметика**: колонка ссылки
хранится как TEXT (`fields.mjs`), `id` — INTEGER, и `t1."order" = t0."id"` даёт
SQLite сравнение с числовой аффинностью — индекс по `item.order` не используется,
подзапрос сканирует таблицу на каждый заказ (проверено `EXPLAIN QUERY PLAN`; тест
«subquery is joined through the ref index» и мутация). Алиасы `t0…tN` по глубине
вложенности: имена колонок без квалификатора внутри подзапроса всегда
резолвятся в его собственную таблицу, наружу торчит только `tK."id"`. Масштаб выше
1e6 (`exact()` округляет до 6 знаков, целые перестают совпадать) не компилируется —
ни у вложенного `sum`, ни у `+`/`-`. Максимальная вложенность — 5.

**Item 3: даты и время.** `date`/`time` — TEXT; `expr.mjs` сравнивает их как *строки*
(`a < b` на строках), а не как моменты. Значит сравнение как строки в SQLite
(BINARY-коллация — порядок кодовых единиц, для ASCII тот же) даёт тот же ответ
при любом формате хранимого `time` (`…10:00:00.000Z` < `…10:00:00Z`, потому что
`.` < `Z`, хотя момент один — так JS отвечал всегда; тест на 5 форматов).
Литералы — только строго `\d{4}-\d{2}-\d{2}` и `…T[0-9:.Zz+-]*` (остальное
не компилируется: в SQL-текст ничего чужого не попадает). Сравнение
числа с датой и `truthy(date)` не компилируются. `min`/`max` по date/time
возвращают текст (`finalizeOne`), `sum`/`avg` по дате — нет. `today`/`now`
компилируются: значение берётся из *того же* единственного clock, что читает
`evaluate()` — `Store#derived` читает `new Date()` один раз (или берёт
`cache.clock` страницы) и передаёт его через `RowCtx` во вложенные производные
поля, хопы и дочерние строки; `evaluate()` передаёт этот clock в
`ctx.agg(node, clock)`, SQL связывает его именованными `$today`/`$now`
(node:sqlite принимает объект именованных параметров плюс позиционные для
`IN (?,…)`). Пакет, посчитанный для другого clock, не читается (`aggValue`).
Раньше каждое вложенное производное поле читало собственный `new Date()`; теперь
одни часы на вычисление — как обещает комментарий в `expr.mjs` («выражение не может
пересечь полночь на полпути»). Тест с часами, тикающими на каждый `new Date()`.

**Что остаётся в JS**, и почему: деление и дробный литерал (сумма float-делений в
SQLite — компенсированная, в JS — наивная, последний разряд может разойтись);
хоп через ссылку и `row.*`; сравнение text/enum/ref; любая функция кроме `if`;
внутренний `avg`; производное money*money и int из money; произведение с более чем
6 знаками (четыре денежных множителя); целое за пределами SQLite/JS (переполнение `SUM`,
значение > 2^53 — `guarded` откатывает *этот* агрегат в JS при исполнении, любая
другая SQL-ошибка остаётся ошибкой); рекурсия за границами.

**Найденное расхождение 0.1.2, оставленное как есть.** Property-тест по случайным
деревьям (ниже) сначала не нашёл его — данные не совпадали на равенстве — но
разбор границы показал: `evaluate()` умножает *двойные мажорных единиц*
(`3 * 0.1 = 0.30000000000000004`), SQL — точные целые. Сумма, `+`/`-` и округление
производного поля поглощают эту пыль (`exact()`, `toMinor`), а сравнение сырого
произведения с точно равным значением — нет: `count(C: qty * price > disc)` при
qty=3, price=0.1, disc=0.3 — 0 в SQL 0.1.2 и в новом коде, 1 в JS (и в 0.1.0/0.1.1,
где такого агрегата ещё не компилировали); `qty=100, price=0.07` против 7 — то же.
Воспроизведение — сам тест «known 0.1.2 divergence». Ответ по правилу раунда
(«ответы маршрутов побайтно те же, что в 0.1.2») **не менялся**; тест
«known 0.1.2 divergence» фиксирует его, чтобы он не рос, и переворачивается
одним условием (отказ компилировать сравнение с «пыльным» операндом,
`a.dusty || b.dusty` в `compileCmp`); новые формы его не расширяют — вложенный
`min`/`max` над сырым произведением не компилируется (иначе сырой double встретил
бы сравнение). Генератор property-теста не подставляет сырое произведение в
сравнение — иначе тест проверял бы этот известный случай, а не остальное.

**Тесты.** `tests/aggfuzz.test.mjs` — property-тест по *случайным деревьям
выражений* с фиксированным seed (`FUZZ_SEED`/`FUZZ_ROUNDS` расширяют поиск из
shell): трёхуровневый граф Parent → Child → Grand, у Child — производные скаляры

**Item 5: память.** «RSS после /dashboard + /Order.csv на графе бенча ×4»
(`mem.mjs`: 2000 клиентов, 8000 заказов, 40 000 позиций, файл SQLite): 0.1.0 —

Что это такое: `process.memoryUsage()` после GC показывает живых ~8 МБ кучи, а
`v8.getHeapStatistics()` сразу после запросов — `total_heap_size` 45–52 МБ; с
`--max-semi-space-size=1` тот же прогон даёт RSS ~100 МБ вместо ~125. То есть рост —
не удержание данных, а **выросшая молодая генерация V8 от числа аллокаций** на строку
(сэмплирующий профиль аллокаций через `inspector`: `hydrate` ≈ 27 МБ, `listRaw` ≈ 7,
результат `GROUP BY` ≈ 7, `evaluate` ≈ 6). Что сделано: `Store#ctx()` создавал на каждое
производное поле каждой строки объект с тремя замыканиями — теперь класс `RowCtx`
(`store/ctx.mjs`): аллокации `hydrate` 26.9 → 21.7 МБ, RSS 124 → 121; `aggKey` (склейка
SQL-текста, который с производными телами стал килобайтами) считался на каждую
строку каждого агрегата — теперь один раз в плане. Что не сделано и почему: самый
крупный источник остался — дашборд/график по производному полю
(`aggregateInMemory`) гидратирует каждую строку только чтобы сгруппировать и
просуммировать; протолкнуть это в SQL — отдельная возможность с собственным
пространством паритета (порядок групп = первое появление в списке `id DESC`,
сортировка NULL, `groupUnit` через `slice`, а не `strftime`) — следующий раунд, вместе со

## Раунд 11 — ящик доставляет строку один раз

`tests/outbox.test.mjs` +7 тестов: два `flush` через `Promise.all` с
транспортом, который ждёт `setTimeout`, — каждая строка доставлена ровно раз и работа
разделена между вызовами; захват достаётся одному и не достаётся `sent`; застрявшая
`sending` не доставляется за миллисекунду до конца аренды и доставляется в момент её
конца (часы внедряются через `opts.now`); база, созданная старым DDL без `claimedAt`,
получает колонку на месте и сохраняет строки; экран `/outbox` показывает `sending` без
кнопки повтора; медленная доставка с истёкшей арендой не затирает результат второго `flush` (строка хранит второй результат, запоздалая запись трассируется как `stale`), `outboxFinish` пишет только под своим `claimedAt`. Мутации: 9 новых (**152 из 152 убито**): снят охранник `status='queued'`,
проигнорировано число изменённых строк, инвертировано сравнение аренды, `flush` доставляет
незахваченное, просроченная аренда не подхватывается, старая таблица не мигрирует, итоговая запись без `claimedAt`, без `status='sending'`, проигравшая доставка выдаётся за результат.

## Раунд 12: точная арифметика денег в JS

Расхождение 0.1.2 («Найденное расхождение», выше — остаётся как история) закрыто со
стороны JS: `evaluate()` теперь пропускает каждое `*` через `exact()` (округление до 6
знаков), как уже делали `+`, `-`, `sum`, `avg`. `3 * 0.1` — `0.3`, `qty * price > 0.3`
ложно и в JS, и в SQL, и в десятичной арифметике. Деление не тронуто (частное — дробь).
Компилятор: `dusty` удалён целиком (мёртв — вложенный `min`/`max` над сырым
произведением теперь компилируется, паритет доказан); произведение с масштабом > 1e6
(больше 6 знаков — четыре денежных множителя) не компилируется, чтобы JS и SQL не
округляли в разных местах (это же условие защищает `+`/`-`; прежняя проверка масштаба у
вложенного `sum` стала недостижимой и удалена вместе со своей мутацией).

Тесты: закреплённый тест «known 0.1.2 divergence» превращён в паритет (JS == SQL ==
точная десятичная арифметика, включая `>`, `>=`, `=` и вложенные `min`/`max`);
`aggfuzz` подставляет сырые произведения в сравнения, вложенные `min`/`max` и int-агрегаты,
а строки на четверть строятся с `disc == qty * price` (без такого смещения ничьи
случайно не встречались, и откат `exact()` фуззер не замечал; с ним — ловит за 1–3
раунда). Мутация: `*` без `exact()`.

## Временные каталоги

Каждый каталог, который создаёт тест, идёт через `tmpDir(prefix[, t])` из `tests/helpers.mjs`:
он удаляется при выходе процесса файла (и сразу после теста, если передан `t`), в том числе
после падения; `boot().close()` удаляет свой каталог. `tests/coverage.mjs` гоняет набор с
приватным `TMPDIR` и падает, если там что-то осталось; `tests/mutate.mjs` даёт каждому прогону
свой `TMPDIR` и удаляет его, даже когда прогон убит по таймауту (~180 прогонов больше не
забивают inode-ы tmpfs).
